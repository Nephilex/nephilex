    Benchmarks & accuracy¶

    A scanner's most important number is how accurate it is, and the most honest thing a young scanner can do is publish that number with its methodology, and republish it when it gets worse. Nephilex measures accuracy three ways: a small in-repo labeled corpus, public labeled datasets scored side by side with Bandit and Semgrep, and finding inventories on large reference apps.

    Labeled corpus (precision and recall)¶

    A small, fully labeled corpus ships in the repo so the numbers are reproducible on any machine with one command and no downloads:

    python benchmarks/accuracy.py

    Every case is a single file that is either vulnerable (Nephilex must raise at least one actionable finding) or safe (Nephilex must raise none). From that:

    • Recall = caught vulnerable cases / all vulnerable cases (did we miss a bug?)
    • Precision = caught / (caught + findings on safe cases) (did we cry wolf?)

    Current results:

    Domain Recall Precision Vulnerable cases Safe cases False positives
    secrets 100% 100% 1 1 0
    sast 100% 100% 7 9 0
    taint 100% 100% 22 22 0
    iac 100% 100% 1 1 0
    llm 100% 100% 17 17 0
    mcp 100% 100% 7 7 0
    malware 100% 100% 4 5 0
    overall 100% 100% 59 62 0

    Read this number honestly

    This is a small sanity-and-regression corpus (59 vulnerable, 62 safe cases), not a claim of 100% real-world accuracy. 100% here means Nephilex classifies every case in this set correctly, and the run exits non-zero if it does not, so a regression fails CI. On independent public datasets the numbers are far lower; see the next section.

    The llm rows are worth calling out: there is no standard public benchmark for LLM/AI-application vulnerability classes (prompt injection, insecure model-output handling, unsafe model loading, secrets in prompts, excessive agency). This labeled set covers OWASP LLM01/02/05/06/08 with a vulnerable and a safe case each, so the accuracy claim in Nephilex's strongest and least-crowded domain is measurable and reproducible rather than asserted.

    This corpus already earned its keep: building it surfaced two real bugs, both now fixed and covered by regression tests:

    • A false negative: subprocess(..., shell=True) was being dropped by the engine whenever the AST taint tier ran, because that tier does not model a taint-independent smell. Command-execution findings now survive.
    • A false positive: a properly parameterized query execute("... %s", (uid,)) was flagged as SQL injection because a tainted value in the bound-parameters argument counted. Bound parameters are now recognized as the safe form.

    Public labeled datasets (Nephilex, Bandit, Semgrep)¶

    The in-repo corpus is written by the same people who write the rules, so it cannot tell you how Nephilex does on code it was not tuned for. For that, Nephilex is scored on two independent, public, labeled Python datasets, next to Bandit and Semgrep run on the same files and scored by the same code.

    Reproduce¶

    pip install -e ".[ast]"                    # Nephilex with the AST tier
pip install bandit semgrep                 # ideally in a separate virtualenv
python benchmarks/public/run.py            # both datasets, all three tools

    Useful variations:

    python benchmarks/public/run.py --dataset owasp-python --tools nephilex,bandit,semgrep
python benchmarks/public/run.py --offline  # re-score cached outputs, no network, no tool runs
python benchmarks/public/run.py --bandit /path/to/bandit --semgrep /path/to/semgrep

    --bandit and --semgrep (or the NEPHILEX_BENCH_BANDIT and NEPHILEX_BENCH_SEMGREP environment variables) point at tools installed outside the current environment. A tool that cannot be found is recorded as not_run with the reason; no numbers are produced for it.

    Outputs:

    • benchmarks/results/public/<dataset>.json: dataset commit and archive hash, tool versions, run dates, command lines, the CWE mapping tables used, per-rule CWE inventory, and per-category and overall metrics for every tool and mode, including the list of false-positive and false-negative case ids.
    • benchmarks/results/public/SUMMARY.md: generated tables.
    • benchmarks/results/public/findings/<dataset>/<tool>.json: every finding normalized to file, line, rule id and CWEs (no source code), so the scoring can be audited or re-run with --offline without installing the tools.
    • benchmarks/.corpora/ (git-ignored): the downloaded datasets, the cached Semgrep ruleset and each tool's raw JSON output.

    Scoring¶

    OWASP BenchmarkPython follows the OWASP Benchmark methodology. A test case is flagged when the tool reports at least one finding in that test case's source file (testcode/BenchmarkTestNNNNN.py) whose CWE matches the case's CWE. Findings in that file with a different CWE are ignored for that case; findings in helpers and templates are ignored. Flagged vulnerable case = TP, flagged safe case = FP, unflagged safe = TN, unflagged vulnerable = FN. Per category and overall: TPR (recall), FPR, precision, F1 and the OWASP score, TPR - FPR. Overall numbers are given two ways: pooled (counts summed over all 1230 cases, which weights large categories such as weakrand with 326 cases) and category average (unweighted mean of the per-category TPR, FPR and score, as on the official OWASP scorecard).

    SecurityEval has no safe samples, so only recall can be measured. Precision, FPR and F1 are undefined and are not reported. A sample is detected when the tool reports a finding in its file with a matching CWE; the any mode also reports how many samples got any finding at all, whatever its CWE.

    CWE matching comes in two modes, both always published:

    • strict: one of the tool's own reported CWEs equals the labeled CWE.
    • mapped: the tool's CWEs, plus documented per-rule overrides, intersect an equivalence group containing the label. The groups join parent and child CWEs (for example 327/328/916 for weak hashing, 22/23/36/73/99 for path traversal, 94/95 for code injection, 330/331/338 for weak randomness). They are in benchmarks/public/mapping.py and apply to every tool equally.

    Manual overrides exist only where a tool reports a generic or wrong CWE for a rule with a single documented purpose. After auditing the per-rule inventory, the overrides are: Bandit's XML blacklist rules B313 to B320 and B405 to B410 (reported as CWE-20, mapped to CWE-611), B506 yaml_load (CWE-20 to CWE-502), B102 exec_used and B307 eval (reported as CWE-78, mapped to CWE-95), and Semgrep's python.flask.security.injection.tainted-sql-string (registry metadata says CWE-704, mapped to CWE-89). No Nephilex rule needed an override. Overrides only add CWEs. Note that they cut both ways: Bandit's mapped OWASP score is lower than its strict one, because the overrides credit rules that also fire on safe cases.

    Methodology checks¶

    Corpus-specific keying. No rule refers to a benchmark file name, test id, helper module or function (helpers.*, the benchmark's request wrapper or HTML-escape helper), variable name, comment, or the expected-results CSV. An audit before publishing removed three things that were closer to the benchmark's own "safe" idioms than to general mitigations: the blocklist guards '../' in p (path traversal) and "contains no quote" (XPath), the .replace("'", ...) XPath sanitizer and the "quoted literal only" check before eval. Those blocklists are incomplete in general (an absolute path or another quoting style gets past them), so the engine no longer trusts them. That costs 66 OWASP false positives (16 path traversal, 38 XPath, 12 code injection), which are in the table above. os.path.exists and other existence checks were also dropped as path sinks after the false-positive check below, which costs 5 path-traversal true positives. One rule that is correct but was motivated by the benchmark stays and is documented: request.path is not a source in a Flask view whose routes have no <converters>, because routing has already fixed the path.

    Split halves (not a held-out test). The OWASP score is stable across halves, but both halves were visible during development, so this shows the rules are not keyed to individual cases, not that they generalise:

    Split Cases Mapped score (pooled) Mapped score (category avg) Strict score (pooled)
    even test numbers 615 +89.4 +92.2 +71.5
    odd test numbers 615 +89.4 +89.0 +70.1
    random half A (seed 20261022) 611 +88.8 +92.7 +70.9
    random half B 619 +90.0 +90.2 +70.7

    SecurityEval (a different corpus). Mapped recall went from 12/121 (9.9%) in 0.9.2 to 32/121 (26.5%). Five of the 32 come from rules added after reading SecurityEval's misses (compile() as a code sink, a redirect through headers["Location"], and lxml resolve_entities=True, three samples); the SQL-from-a-parameter rule was written for a SecurityEval sample named in the task (CWE-089_author_1.py). Without the five post-hoc detections the figure is 27/121 (22.3%). That is the better estimate of how the OWASP-driven work transfers to code it was not developed on: a large gain over 0.9.2, still behind Bandit on CWE-average recall (23.3%) and CWE breadth (21 CWEs).

    False positives on code with no known vulnerabilities. The SAST, taint and auth scanners (ast-python, ast-python-xfile, patterns, authz) were run on Flask 3.0.3's tutorial and JavaScript example apps, the Flask 3.0.3 and Werkzeug 3.0.3 sources, and the installed click, requests, jinja2, rich and typer packages. Findings at severity low or above, 0.9.2 scanners against these changes:

    Project 0.9.2 Now New findings
    Flask tutorial app (flaskr) 0 0
    Flask JavaScript example 0 0
    Flask 3.0.3 3 3 none (the same 3: PYTHONSTARTUP read and executed by flask shell, SHA-1 in sessions)
    Werkzeug 3.0.3 6 7 subprocess.call(args) re-executing sys.argv in the reloader

    The two new findings come from treating sys.argv as an untrusted source, which Nephilex already did in 0.9.2; the new engine simply follows those flows further. Earlier drafts of this change were noisier on these projects (eval/exec of a function parameter in template engines, os.path.exists on environment paths, x.open() on test clients, http.cookiejar set_cookie(cookie) and set_cookie(..., **kwargs)); those rules were removed or narrowed before publishing.

    What changed since 0.9.2¶

    Each fix below is a general rule meant to hold on real code. Details per rule are in Scanners.

    • Flow-sensitive taint. Branches, match, loops and try are analyzed separately and joined, so if not p: p = "" keeps the taint (the idiom behind 41 of the 80 false negatives in 0.9.2). Conditions that fold to a constant prune the dead branch. Literal dicts, lists and configparser objects are tracked per key.
    • Guards. Early returns on complete mitigations refine the value after them: allowlist membership, isdigit()-style checks, a urlparse(u).netloc allowlist, and a resolved-path containment check.
    • Sources. Methods that return request data (request wrappers) are sources when called on an object built from the request, in the same file or across files. request.path is not a source in a view whose routes have no converters.
    • New Python rules. Reflected XSS from view return values and Markup, |safe in templates, open redirect, XXE with external entities enabled, LDAP and XPath injection, trust boundary (session stores), weak randomness for tokens and session values, hashlib.new("md5"), pathlib file access, compile() as a code sink, and set_cookie() without secure=True (CWE-614) or httponly=True (CWE-1004).
    • Fewer sink-only findings. shell=True, os.system and pickle.loads whose payload is built only from literals are no longer reported. yaml.load with an unsafe loader is still reported, graded by taint.
    • Function parameters. SQL built by formatting a function parameter is reported at low confidence. The regex tier used to catch some of these, but the engine dropped its CWE-89 findings wherever the taint tier ran.

    What the numbers say¶

    • On OWASP BenchmarkPython Nephilex now scores +89.4 pooled and +91.3 by category average (mapped), against +18.6 and +7.5 for Bandit and +14.2 and +6.0 for Semgrep. Because the rules were developed with this dataset visible and it is generated from a small set of templates, read this as "Nephilex handles the idioms in this benchmark", not as a real-world detection rate.
    • The 74 false positives are 66 cases guarded only by blocklist checks that Nephilex deliberately does not trust (see above), 5 yaml.load(..., Loader=yaml.Loader) calls on a constant document (an unsafe loader is still reported, at low severity, because it is wrong code even when today's input is constant), and 3 payloads that come from a wrapper method in another file returning a constant, which the regex tier, grading one file at a time, cannot see.
    • Strict mode (+70.8) is lower mainly because Nephilex reports MD5/SHA-1 as CWE-327 against the benchmark's CWE-328 label (71 cases) and eval/exec as CWE-95 against its parent CWE-94 (20 cases); the other 5 misses are the path-traversal cases whose only sink is an existence check.
    • On SecurityEval Nephilex ties Bandit on mapped recall (32 samples each) but trails it on CWE-average recall (18.4% vs 23.3%) and CWE breadth (17 vs 21 CWEs). Without the detections from rules added after reading SecurityEval, Nephilex is at 27 samples. SecurityEval covers many classes Nephilex has no Python rule for (hard-coded passwords as CWE-259, log injection, temporary files, regex DoS, SSRF), and most samples are helper functions with no web request.

    Limitations¶

    • Labeled-dataset bias. OWASP BenchmarkPython is synthetic: every case is generated from templates, uses Flask, and contains deliberate traps (dead branches, constant conditions, overwritten values) that reward or punish specific analysis features. Category sizes are uneven (326 weakrand cases, 16 sqli cases), which dominates the pooled numbers; the category average is published for that reason. Real applications look different.
    • SecurityEval has no negatives, so it cannot measure false positives at all, and most CWEs have one to six samples. Many samples are snippets whose input is a function parameter rather than a web request, which penalizes tools that require a proven untrusted source (the Nephilex taint tier) relative to tools that flag sinks unconditionally (Bandit).
    • CWE mapping caveats. Tools pick different CWEs for the same issue (MD5 is CWE-327 in Bandit, Semgrep and Nephilex, but the benchmark label is CWE-328), so strict understates every tool and mapped depends on the committed groups and overrides. Both are published; the mapping tables are embedded in each results file.
    • Python only. These datasets measure the Python SAST and taint tiers. They say nothing about Nephilex's JavaScript/TypeScript tiers, secrets, dependency, IaC, container or LLM-application scanners.
    • Default configurations only. Semgrep was run with the p/python registry ruleset on the Community Edition engine (no cross-file Pro analysis); another ruleset (for example p/default) or Semgrep Pro would give different numbers. Nephilex was run without an AI provider (--no-ai), so AI triage is not measured. Bandit and Semgrep were not tuned for these datasets. Nephilex's rules were revised after studying its OWASP misses, with no case held out (see "Methodology checks"); no rule refers to a benchmark file, test id, helper or generated name.
    • Single run, single machine. All three tools are deterministic for a fixed input, but the runs were made once, on Windows. Nephilex's default scanner set includes a dependency scanner that may query OSV for the dataset's requirements.txt; those findings fall outside the test cases and do not affect the scores.

    Held-out benchmark: real fix commits¶

    The public datasets above have a known weakness: Nephilex's Python rules were revised with OWASP BenchmarkPython visible. This benchmark answers that with code nobody tuned anything on: real vulnerabilities from real projects, taken as before/after pairs from the commits that fixed them. This is the frozen v1 set; a development set and a time-split test set use the same rule (see "Three benchmark sets" below).

    Selection rule¶

    The rule was written down and committed (in benchmarks/heldout/selection.py, with the resulting manifest) before any tool was run on the selected files. Git history shows the order. In full:

    1. Source. GitHub Advisory Database, reviewed advisories only, ecosystems pip and npm, published from 2024-01-01 to 2026-09-30, not withdrawn.
    2. CWE. The advisory lists at least one CWE that Nephilex's Python or JavaScript/TypeScript source-code rules report, or a member of the equivalence group that contains one (benchmarks/public/mapping.py). The claimed CWEs, with the scanner modules that report them, are recorded in the manifest: 22, 73, 74, 77, 78, 79, 80, 89, 90, 94, 95, 295, 306, 327, 330, 338, 347, 352, 489, 501, 502, 598, 601, 611, 614, 639, 643, 918, 1004, 1336. With their groups the target set adds 23, 36, 88, 99, 297, 328, 331, 564, 776 and
    3. CWEs reported only by configuration, infrastructure, dependency, CI, secret, other-language or LLM-misuse rules (for example 200, 250, 732) are not claimed here: those rules detect them only in narrow contexts. A case's label is the subset of its advisory's CWEs that is in the target set.
    4. Fix commit. At least one advisory reference is a GitHub commit URL (/commit/<sha> or /pull/<n>/commits/<sha>). All such commits are used.
    5. Files. From each fix commit, every modified or renamed .py, .js, .mjs, .cjs, .jsx, .ts, .mts, .cts or .tsx file, except tests (test/tests/spec/__tests__/e2e directories, test_*.py, *_test.py, test.py, tests.py, conftest.py, *.test.js, *.spec.ts and similar), documentation and examples (doc, docs, example(s), sample(s)), vendored or build output (vendor, third_party, node_modules, dist, build, coverage, ...), minified or generated files (*.min.js, bundles, *_pb2.py) and TypeScript declarations (*.d.ts). Files the fix added or deleted have no before/after pair and are skipped. Within one advisory a path is taken once, from the first commit that touches it; a file and commit already used by another advisory is not used twice.
    6. Localized fixes. An advisory whose fix touches more than 5 eligible files is dropped as a refactor: most of its changed lines would not be the vulnerable code.
    7. Sampling. Candidate advisories are ordered by SHA-256 of their GHSA id, a fixed order nobody chose, and taken until 120 pip and 80 npm cases are reached. Nothing in the order depends on any tool.

    A case is one file of one advisory. The vulnerable version is the file at the fix commit's first parent; the patched version is the file at the fix commit. The manifest (benchmarks/heldout/manifest.json) records for each case the advisory id, CVE, CWEs, repository, parent and fix SHAs, paths, the changed line ranges on both sides and the SHA-256 of both versions, so anyone can re-fetch and verify exactly the same files. It also lists every dropped advisory and file with its reason.

    Changed lines come from the fix commit's unified diff: removed lines on the vulnerable side and added lines on the patched side. A hunk that only inserts lines marks the two vulnerable-side lines around the insertion point, and a hunk that only deletes marks the two patched-side lines around the deletion.

    Scoring¶

    Fixed with the selection rule, before any tool ran:

    • Window. A finding belongs to a case when it is in the case's file and its line is within 3 lines of a changed line on that side. Windows of 0 and 10 lines are published as a sensitivity check.
    • CWE match. mapped (primary): the finding's CWEs, plus the documented rule overrides, intersect the equivalence group of one of the case's label CWEs, exactly as in the public benchmark (benchmarks/public/mapping.py, unchanged). strict: a finding CWE equals a label CWE. any: any finding in the window, whatever its CWE.
    • Detected. The vulnerable version has a matching finding in the window around its changed lines.
    • Flagged after the fix. The patched version has a matching finding in the window around its changed lines. Still flagged counts detected cases that are also flagged after the fix.
    • Recall = detected / cases. Fix-aware recall = (detected and not flagged after the fix) / cases: the tool told the vulnerable version apart from the patched one.
    • Precision proxy = detected / (detected + flagged after the fix), treating every match on fixed code as a false positive. Real advisories have no labeled safe code, so this is a proxy, not precision (see Limitations).
    • Results are given per case (file) and per advisory (an advisory is detected when any of its files is), by CWE, language and ecosystem, with raw counts. A case with two label CWEs counts once in each CWE row.

    What the numbers say¶

    • On real fix commits, all three tools find very little. Nephilex detects 4 of 201 cases (2.0%), the same count as Semgrep; Bandit detects 12 of its 118 Python cases (10.2%). Against the +89.4 OWASP score above, this is the number to quote for code Nephilex was not developed on.
    • Bandit's lead comes from flagging sinks without asking where the data came from. Six of its 12 detections are eval() (B307, credited to CWE-94/95 by the committed override), two are shell=True and two are SQL built by string formatting. Real library advisories often have a public function parameter as the attacker-controlled input, which a sink-only rule catches and a source-to-sink taint rule does not.
    • Where Nephilex detected, three of its four detections came from the regex patterns tier (child_process.exec in two JavaScript files, pickle.loads in LangChain's FAISS loader); the fourth is the low-confidence AST rule for SQL formatted from a non-constant value with no traced source (LlamaIndex DuckDB retriever). None of the four is a traced flow from an untrusted source to a sink, the analysis behind the OWASP results.
    • Misses worth reading include Parsl (%-formatted SQL from a Flask route parameter passed to pandas.read_sql_query) and PaddlePaddle (shell=True with an f-string of a URL parameter), both found by Bandit and Semgrep. They are recorded, not fixed: no Nephilex rule was changed because of this benchmark.
    • Flagged after the fix is rare for every tool in mapped mode. Nephilex's one case is the LangChain loader, where the fix kept pickle.loads behind an opt-in flag, so the finding is arguably still correct. In any mode, Nephilex matches 6 fixed files: besides that one, cookie-flag, OAuth state and race-hint findings near the changed lines of open-redirect and XSS fixes (they name other weaknesses), and a command-injection finding in the patched MLflow file of a code-injection advisory.

    Limitations¶

    • Single-file view. Each case is only the changed file, not the repository. A flow whose source is in another file (a route handler calling a helper) is invisible to every tool. This handicaps taint-based analysis (Nephilex, Semgrep's taint rules) more than sink-only rules (Bandit).
    • Changed lines are a proxy for the vulnerable lines. A fix can add a check far from the sink, or touch several files of which one holds the bug. The window, the 5-file cap and the per-advisory roll-up limit this, they do not remove it.
    • The precision proxy is not precision. A match on the patched lines may still be a real issue (as in the LangChain case), and findings outside the changed lines are not counted at all, so a tool that reports a lot elsewhere in the file pays nothing. There is no labeled safe code in this benchmark.
    • Advisory CWE labels are noisy. Authors pick broad (CWE-74) or neighbouring CWEs; the any mode is published for that reason.
    • Small sample. 201 cases from 117 advisories, with most CWEs under 15 cases and none for CWE-611. Per-CWE rows are anecdotes, not rates.
    • Snapshot. The Advisory Database changes; the manifest freezes the 2026-10-23 selection. The selection rule was amended once before any score existed (see "Amendment" above).
    • Default configurations only, as in the public benchmark: Semgrep CE with two registry rulesets, Bandit defaults, Nephilex without AI triage. Semgrep timed out on some rules for 22 large case versions.

    Time-split test set: the rule¶

    The rule is committed (timesplit_rule in benchmarks/heldout/selection.py, the guard in benchmarks/heldout/cli.py, the description in benchmarks/heldout/sets/timesplit/README.md).

    • Window. Reviewed pip and npm advisories published from 2026-10-01 up to and including --until, which must be before the day of selection (UTC) so the window is closed. The API's date filter is re-checked on each advisory's published_at.
    • Same rule as v1 for CWEs, fix commits, files and the 5-file cap.
    • Exclusions. Every advisory the v1 or development selection examined, any advisory sharing a CVE id with one of them, and any file and commit that is already a v1 or development case.
    • Sampling. SHA-256 of "timesplit:" plus the upper-cased GHSA id, up to 200 pip and 150 npm cases.
    • Freeze guard. select --set timesplit refuses to run, before any request, without --rules-frozen-at <full commit sha>, and unless src/nephilex in the checkout is identical to that commit. The commit, the harness commit and the time are recorded in the manifest's freeze entry. The set is selected once, and scan --set timesplit refuses to run if src/nephilex no longer matches the frozen commit.
    python benchmarks/heldout/run.py select --set timesplit \
    --until YYYY-MM-DD --rules-frozen-at <full commit sha>

    • Findings outside the changed lines. Reading them: a zip-slip extraction in Weblate's backup restore (member names checked only with normpath) and a reflected XSS in a changedetection.io Flask route (the very bug of that advisory, but outside its changed lines) are real; a flow through an imported safe_join_path helper (xiaomusic) is most likely a false positive, because a helper in another file is not summarized; gradio's file route has its own allowlist logic that is not modeled.
    • Flagged after the fix stays at the baseline's 4 cases: SQL built with an f-string in two LangGraph SQLite checkpoint files, an open redirect in a Khoj auth router, and pickle.loads in the pdfminer CMap loader. None is in the CWE classes this work targeted, and the rules that report them did not change. Library mode flags the same four.

    Public reference apps (finding inventory)¶

    The larger harness scans real, known-vulnerable applications:

    python benchmarks/run_benchmarks.py            # all available corpora
python benchmarks/run_benchmarks.py juice-shop # just one

    It publishes a finding inventory (counts by scanner and severity, plus scan time) for OWASP Juice Shop, DVWA, WebGoat, and (with a manual download) NIST SARD/Juliet. An inventory is not precision/recall, it needs a ground-truth mapping per corpus, which is tracked as a ground_truth hook and where contributions are welcome, but it shows coverage shape and catches per-release regressions in what Nephilex finds and how fast.

    Methodology and honesty notes¶

    • Runs are deterministic and offline (--no-ai, caching disabled) so numbers are comparable across machines.
    • Numbers that get worse are published anyway. A benchmark that only ever improves is marketing, not measurement.
    • The labeled corpus is intentionally small and unambiguous. Growing it (more languages, more classes, adversarial safe cases) directly improves the quality signal, and pull requests that add labeled cases are among the most valuable contributions to the project.
