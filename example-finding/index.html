    Example finding: unsafe yaml.load¶

    This page follows one real finding from the demo app in examples/vulnerable-app from the vulnerable line to a committed fix and a re-scan. It was chosen because the untrusted input and the dangerous call are both visible, Nephilex uses data flow to grade it, and Nephilex has a deterministic fix for it.

    Everything below was produced by Nephilex 0.11.0 on 2026-10-23 with --no-ai (no AI provider, no API key). The commands are the ones from the Quickstart; outputs are pasted as printed, trimmed only where marked.

    The vulnerable code¶

    examples/vulnerable-app/app.py, lines 41 to 45:

    41
42
43
44
45
    @app.route("/config")
def load_config():
    # Unsafe deserialization (patterns scanner: CWE-502).
    raw = request.args.get("data")
    return str(yaml.load(raw))

    Line 44 reads the data query parameter, which anyone who can reach /config controls. Line 45 passes it to yaml.load without a safe loader, which can build arbitrary Python objects from the document.

    How Nephilex reports it¶

    The row in the terminal table of nephilex scan nephilex/examples/vulnerable-app --no-ai (trimmed to this one row):

    │ High     │ 70.5 │ Unsafe yaml.load without          │ app.py:45        │ patterns.python-yaml-load        │
│          │      │ SafeLoader                        │                  │                                  │

    The same finding in the Markdown report (nephilex scan nephilex/examples/vulnerable-app --no-ai --patches -f json -f markdown -o ex, file ex/nephilex-report.md, finding 6 of 20):

    ### 6. [HIGH] Unsafe yaml.load without SafeLoader

- **Severity:** High (risk 70.5/100), **Confidence:** High, **Likelihood:** Possible
- **Location:** `app.py:45`
- **Scanner/Rule:** `patterns` / `patterns.python-yaml-load`
- **Mapping:** CWE-502, A08:2021-Software and Data Integrity Failures

```
    return str(yaml.load(raw))
```

**Why it's a vulnerability:** yaml.load with the default loader can construct arbitrary Python objects from the document.

**How an attacker exploits it:** Feed a YAML payload using \`\!\!python/object/apply\` tags to execute code.

**Business impact:** Remote code execution.

**Remediation:** Use yaml.safe\_load, or yaml.load\(..., Loader=yaml.SafeLoader\).

**Suggested patch (verified):**
```diff
--- a/app.py
+++ b/app.py
@@ -45 +45 @@
-    return str(yaml.load(raw))
+    return str(yaml.safe_load(raw))
```

    Reading the fields¶

    Field Value Where it comes from
    Rule patterns.python-yaml-load A rule in the patterns scanner, which matches source lines; see SAST (pattern rules).
    Severity High (3) The rule's severity: an unsafe YAML loader on input can lead to code execution.
    Confidence High (2) Raised from the rule's default because the data-flow engine found that the argument comes from request data ("dataflow": "tainted").
    Likelihood Possible (2) The pattern scanner's default.
    CWE / OWASP CWE-502, A08:2021 Deserialization of untrusted data; Software and Data Integrity Failures.
    Risk 70.5, contextual 80.5 The risk score combines severity, confidence and likelihood; the contextual score adds 10 because the severity is High or above. See Risk score.

    The JSON stores severity, confidence and likelihood as numbers: severity runs from 0 (Info) to 4 (Critical), confidence from 0 (Low) to 2 (High), likelihood from 0 (Rare) to 4 (Almost certain).

    The confidence grade depends on the [ast] extra. The same scan with a plain pip install nephilex (no tree-sitter) reports this finding with confidence Medium (1), no dataflow key, and risk 64.2.

    Source to sink¶

    Nephilex does not print a step-by-step path for this finding. What it records is the data-flow verdict for the call on line 45, "dataflow": "tainted": the argument to yaml.load was traced back to request data. The source (line 44, request.args.get) and the sink (line 45, yaml.load) above are read from the code, not from the report.

    Versions after 0.11.0 do record this path: every finding has an evidence block with a grade, the steps from source to sink and how to verify it. For this finding the path is request.args.get("data") (line 44), assigned to raw (line 44), passed to yaml.load (line 45), graded likely. See Evidence and grades.

    Two other results point at the same line:

    • The taint scanner reports ast-python.ast-xss on line 45 (Medium): the parsed request data is returned from a Flask view as the response body.
    • The taint scanner also traces the request data into yaml.load on this line. Both tiers report the same weakness, so Nephilex keeps one finding: the pattern finding, because it carries the deterministic fix. nephilex scan and nephilex check make the same choice.

    Verification status¶

    "Verified" has a narrow, checkable meaning in Nephilex 0.11.0:

    1. The rewritten line no longer matches the rule (or matches the rule's recognized safe form). This check runs both for --patches and for nephilex fix.
    2. nephilex fix also re-parses the whole changed file for Python, JSON and YAML files, and drops all fixes for a file that would no longer parse.

    By default it does not run your tests, start the application, or prove that the new code behaves the same. nephilex fix --verify-with-tests adds that check: it runs your test command before and after the fixes in a temporary copy of the repository and commits only fixes that keep the tests passing (see Fixing & pull requests). Either way, review the change as you would any other pull request.

    The re-scan of the fixed branch (nephilex scan . --no-ai -q), trimmed to the summary and the rows for app.py:45. The first line is the folder name, which was fixrepo in this run:

    The yaml.load finding is gone, and so is the other fixed finding (21 before, 19 after). The cross-site scripting finding on the same line is still there: safe_load stops object construction, but the view still returns request data as HTML. One fixed finding does not make the line safe.

    Why the weak hash on line 50 is not fixed

    hash_password hashes a password with MD5. Swapping in SHA-256 would make the rule stop matching, but SHA-256 is also a fast hash, so stored passwords would stay easy to crack. Password storage needs a slow key-derivation function (bcrypt, scrypt or Argon2), which a one-line rewrite cannot introduce. Nephilex therefore offers no automatic fix for a line that hashes a password or secret, and the finding stays with that guidance. Treat verified fixes as a correct first step, not the last one.

    Reproduce it¶

    pipx install "nephilex[ast]"
git clone --depth 1 https://github.com/nephilex/nephilex.git
nephilex scan nephilex/examples/vulnerable-app --no-ai --patches -f json -f markdown -o ex

# nephilex fix needs a git repository of its own:
cp -r nephilex/examples/vulnerable-app demo && cd demo
git init -q && git add -A && git commit -qm "demo app"
nephilex fix --dry-run
nephilex fix -q
nephilex scan . --no-ai -q

    Commit hashes, timestamps, the base branch name (master here, from git's default) and the audit-log actor will differ on your machine, and the dependency findings follow live OSV data. These steps were re-run in a fresh folder for this page and gave the same 21 and 18 finding counts.
